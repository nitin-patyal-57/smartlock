# Smart Lock Monitoring Dashboard

Real-time monitoring for smart locks: **Smart Lock → AWS IoT Core (MQTT) → Node server → Dashboard (WebSocket)**.

MQTT is the only data source. The dashboard makes no REST calls and uses no Firebase. Everything it shows arrives over a single WebSocket from the server, which is the only MQTT client.

## Architecture

```
Smart Lock                 AWS IoT Core               Server (Render)                Dashboard (browser)
┌────────────┐  MQTT/TLS  ┌──────────────┐  MQTT/TLS  ┌──────────────────┐   /ws     ┌──────────────────┐
│ publishes  │──────────▶│ soundbox_dev/ │──────────▶│ Node + mqtt.js   │─────────▶│ React + Vite     │
│ metrics,   │           │  {imei}/      │           │ SQLite (cache)   │◀─────────│ lock registry in │
│ acks       │◀──────────│  metrics|ack| │◀──────────│ alerts/activity  │ requests │ localStorage     │
└────────────┘  commands │  command      │  publish  └──────────────────┘          └──────────────────┘
```

- The server subscribes **only to registered locks** (`soundbox_dev/{imei}/metrics` and `/ack`). There are no wildcard subscriptions. Messages from unregistered IMEIs are ignored.
- Alerts (low battery, tamper, forced unlock, …) and activity (lock/unlock, door open/close, tamper, remote commands) are generated by the server from MQTT state changes.
- Commands (relay, LED, status) are published to `soundbox_dev/{imei}/command`.

### Persistence (Render free tier)

The free Render instance has no persistent disk and sleeps after ~15 minutes without traffic, so the server's SQLite database is only a working cache:

- **Registered locks** are remembered by the browser (`localStorage` key `smartlock_registry_v1`). After every (re)connect the dashboard sends that list to the server (`sync_devices`), which re-subscribes to each lock.
- **Alerts, activity and location history** only cover the time since the server last woke up. While the server sleeps nothing is subscribed, so telemetry from that period is not captured.

## Adding and removing locks

- **Add:** Smart Locks page → *+ Add Lock* → enter the IMEI.
- **Remove one:** trash icon on the lock's card/row on the Smart Locks page.
- **Remove all:** *Remove All Locks* on the Smart Locks page, or Settings → *Remove All Locks & Reset*.

Removing a lock deletes it from the server, **unsubscribes its MQTT topics**, deletes its history/alerts/activity, and removes it from every connected dashboard's registry. It will not come back unless its IMEI is added again. (A browser that was closed when the lock was removed still has it in its registry and will re-add it the next time it connects; remove it again from that browser.)

## Quick start (local)

```bash
# Terminal 1 - server (MQTT bridge + WebSocket) on http://localhost:3001
cd server
npm install
npm run dev

# Terminal 2 - dashboard on http://localhost:3000
npm install
npm run dev
```

To test without hardware, publish simulated metrics for an IMEI to AWS IoT, then add that IMEI in the dashboard:

```bash
cd server
npm run simulator -- 861185084122685
```

## WebSocket protocol (`/ws`)

Client → server: `{ "type": "...", "reqId": "...", "payload": { ... } }`, answered by a `response` event.

| type | payload | purpose |
|------|---------|---------|
| `sync_devices` | `{ devices: [{ imei, deviceName?, modelId? }] }` | Re-register the browser's locks; returns `{ devices, alerts, activity }` |
| `add_device` | `{ imei, deviceName?, modelId? }` | Register a lock and subscribe to its topics |
| `delete_device` | `{ deviceId }` | Remove a lock and unsubscribe |
| `clear_devices` | – | Remove all locks |
| `relay` | `{ deviceId, relay: 1\|2, state: "on"\|"off" }` | Publish relay command |
| `led` | `{ deviceId, led, state, duration_s? }` | Publish LED command |
| `status_query` | `{ deviceId }` | Publish status command |
| `get_history` | `{ deviceId, from?, to? }` | Location history since server start |
| `ack_alert` / `ack_all_alerts` | `{ id }` / – | Acknowledge alerts |

Server → client events: `response`, `device_update`, `device_deleted`, `devices_cleared`, `alert`, `alerts_acknowledged`, `activity`, `device_ack`.

`GET /api/health` remains for uptime checks only; the dashboard does not use it.

## Configuration

### Server (environment)
```
PORT=3001
MQTT_BROKER_URL=mqtts://<your-endpoint>.iot.ap-south-1.amazonaws.com:8883
DATABASE_PATH=./data/smartlock.db
```

### Dashboard (`.env.production`)
```
VITE_WS_URL=wss://smartlock-wi03.onrender.com/ws
```
If `VITE_WS_URL` is unset the dashboard connects to `/ws` on the host that served it. On `localhost` it always uses `ws://localhost:3001/ws`.

## Deploying to Render

`render-build.sh` builds the dashboard, builds the server, and copies the dashboard into `server/public`, so one Render web service serves both the UI and `/ws`.

## Tech stack

**Dashboard:** React 19, TypeScript, Vite 8, Tailwind CSS v4, React Router v7, Recharts, Leaflet, Lucide React

**Server:** Node.js, Express (static files + health), WebSocket (ws), mqtt.js, SQLite (better-sqlite3)
